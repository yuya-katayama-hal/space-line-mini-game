# NFCチェックイン(NTAG 424 DNA)

登録した本人がブースに来たことを、ブースのNFCタグへのタッチで確かめます。

## 仕組み

1. ブースに **NTAG 424 DNA** のタグを貼ります。タッチのたびに、署名付きのURLを作るタグです:
   `https://space-line-54818.web.app/register/?picc=<32桁>&cmac=<16桁>`
   - `picc`: 暗号化されたタグIDとタッチ回数
   - `cmac`: 署名
2. 来場者が、整理券を受け取ったスマホでタッチします。iPhoneでもAndroidでもアプリなしで登録ページが開き、チェックインの依頼が送られます。
3. **受付PC**(`server/server.ts`)が、受付PCにだけある鍵で次を確かめます。受付の判定ルールは `server/checkin.ts` にあります。
   - 署名が正しいこと(偽造・改ざんの防止)
   - 整理券を作ったスマホからの依頼であること(他人の整理券は使えない)
   - 整理券が終了していないこと
   - タッチ回数が、そのタグで前回受け付けた値より大きいこと(使い回しの防止)
4. 合格すると整理券に来場時刻が記録されます。スマホに「チェックイン完了!」、受付画面に「来場済み ✔」と表示されます。ブースは、呼び出した人がチェックイン済みのときだけ、その人の体験として始めます。

**どこで確認するか**
- 本番(`product`):スマホの依頼を Firestore の `checkins` に書き込み、受付PCがそれを常時見張って答えます。来場時刻とタグの回数は受付PCしか書き込めません(Firestoreのルールで、スタッフのアカウントからも書けないようにしています)。
- 開発(`dev`):受付PCのサーバーが、その場で答えます。

**残るリスク(どの方式でも防ぎきれないもの)**
- ブースでタッチしてURLを保存しておくと、次の本物のチェックインが入るまでの短い間だけ使えます。その後は使えません。
- 共犯者がその場からリアルタイムで中継する攻撃は、NFCだけでは防げません。最後はスタッフが顔を見て確かめます。
- 受付PCを触れる人は鍵を取り出せます。受付PCはスタッフが管理してください。

## 用意するもの

- **NTAG 424 DNA のタグ**:シール型。ブース用1〜2枚と予備。1枚数百円です。NTAG213/215 ではありません。
- **タグを設定する道具**:NXPの無料アプリ「NFC TagWriter by NXP」(Android / iPhone)、またはPCとNFCリーダー+NXP TagXplorer。
- **受付PC**:このプロジェクトと、プロジェクトの外の「鍵フォルダ」。

## 1. 鍵を作る(1回だけ)

受付PCで実行します:
```
node tools/new-keys.ts
```
`C:\Users\<ユーザー名>\spaceline-secrets\sdm-keys.json` に2つの鍵が保存され、画面にも表示されます。
- `metaReadKey`:タグの **SDM Meta Read Key**(タグIDと回数の暗号化に使う)
- `fileReadKey`:タグの **SDM File Read Key**(署名に使う)

注意:
- 鍵フォルダは**プロジェクトの外**に置きます。中に置こうとすると、道具もサーバーも拒否します。
- 鍵のコピーを、USBメモリや紙などオフラインで安全な場所に保管してください。鍵をなくすと、タグを設定し直すことになります。
- 別の場所を使うときは、環境変数 `SPACELINE_SECRETS` にフォルダを指定します。

## 2. タグを設定する(タグごと)

TagWriter(またはTagXplorer)で、次の内容を設定します。画面の名前はアプリのバージョンで違うことがあるので、最後の「3. 確かめる」で必ず確認してください。

- **書き込むURL**:`https://space-line-54818.web.app/register/`
- **SDM(Secure Dynamic Messaging / SUN)を有効**にして:
  - **UIDとSDM Read Counterのミラー**を有効にし、暗号化する(PICCデータ)。パラメータ名は `picc`
  - **SUN/CMAC署名**を有効にする。パラメータ名は `cmac`
  - **CMACの対象データは空**(MAC Input Offset = MAC Offset)。URLの文字まで署名に含める設定だと、受付PCの確認が `bad-signature` になります。
  - **SDM Meta Read Key** に `metaReadKey`、**SDM File Read Key** に `fileReadKey` を割り当てる
- **タグのマスターキー(Key 0)を、初期値(全部0)から変える**。変えないと、誰でもタグの設定を書き換えられます。マスターキーも安全に保管してください。
- 読み取りは誰でもできる設定(スマホがアプリなしで読むため)、書き込みは鍵が必要な設定にします。

## 3. 確かめる(タグごと)

1. スマホでタグにタッチし、開いたページのURLをコピーします。この時点では、そのタッチでチェックインはされません。
2. 受付PCで実行します:
   ```
   node tools/check-tap.ts <picc の値> <cmac の値>
   ```
   (URLを丸ごと `"…"` で渡しても動きますが、Windowsでは `&` で切れることがあるため、2つの値を並べる形が確実です。)
3. `OK  tag UID …, tap counter …` と出れば成功です。`NG` のときは、理由とヒントが表示されます。
4. もう一度タッチして、回数が増えることを確かめます。

## 4. 受付PCの準備(本番)

本番では、受付PCがFirestoreに書き込むためのサービスアカウントが必要です。

1. Google Cloud コンソールで、プロジェクト `space-line-54818` を開きます。**IAMと管理 → サービスアカウント → 作成**。名前は `spaceline-checkin` など。
2. ロールは **Cloud Datastore ユーザー**(`roles/datastore.user`)だけにします。Firestoreの読み書きだけができる、最小限の権限です。
   - Firebaseコンソールの「新しい秘密鍵を生成」で作るアカウントは、プロジェクト全体を操作できる強い権限を持ちます。使えますが、上の最小限のほうを勧めます。
3. そのアカウントの **鍵 → 鍵を追加 → JSON** で鍵ファイルをダウンロードし、`spaceline-secrets\firebase-service-account.json` という名前で保存します(プロジェクトの外)。
4. `start.bat` で起動し、サーバーの窓に次の行が出ることを確認します:
   `NFC check-in → on (answering Firestore check-ins for space-line-54818)`
   `off: …` のときは、その理由が表示されます(鍵がない、プロジェクトが違う、など)。
5. Firestoreのルールと公開ページを**一緒に**デプロイします(`npm run deploy`)。新しいルールは整理券に持ち主(`owner`)を必要とするので、ページだけ、ルールだけの更新は避けてください。

鍵フォルダの中身:
```
C:\Users\<ユーザー名>\spaceline-secrets\
  sdm-keys.json                   タグの鍵(tools/new-keys.ts で作成)
  firebase-service-account.json   本番の確認用(手順4)
```

## 運用

- **受付PCの `server.ts` を動かしたままにします。** `start.bat` は `server/keep-running.bat` の中でサーバーを起動するので、落ちても3秒後に自動で立ち上がり直します。最小化されたサーバーの窓を閉じると止まるので、閉じないでください。止まっている間の依頼は確認待ちでたまり、再開すると古い順に処理されます。
- **うまくいかない来場者には、受付画面の「手動」ボタン(呼び出し中の人は「手動でチェックイン」)を使います。** 本番でも受付PCの確認係を通るので、記録に残ります。
- よくあるケースは、別のブラウザで登録した人です(LINEの中のブラウザで登録して、タッチでSafariが開いた、など)。登録ページが「このブラウザに整理券がありません」と案内します。登録したブラウザで開き直してもらうか、手動チェックインにします。
- **記録:** 受付画面の「記録」に登録数・来場数・体験数が出ます。「CSVを保存」で一覧(番号、ニックネーム、状態、登録時刻、来場時刻)をダウンロードできます。
- **展示会のあと:**
  - Google Cloud コンソールで、サービスアカウントの鍵を**削除**します。
  - 次の展示会では `sdm-keys.json` を作り直し、タグも設定し直すと安全です。

## 開発環境で試す(本物のタグなし)

1. テスト用の鍵フォルダに、全部0の鍵を置きます:
   ```json
   { "metaReadKey": "00000000000000000000000000000000", "fileReadKey": "00000000000000000000000000000000" }
   ```
2. `npm run build:dev` でdev環境のページを作り、`SPACELINE_SECRETS=<そのフォルダ>` で `npm start` します。終わったら `npm run build` で本番用に戻します。
3. タッチの代わりにURLを作ります:
   ```
   node tools/fake-tap.ts <回数>
   ```
   出てきたURLを、整理券を取ったブラウザで開くとチェックインできます。同じURLをもう一度開くと「このタッチは使えません」になります。
   - 鍵を知っていれば誰でも正しいタッチを作れる、ということでもあります。本物の鍵を鍵フォルダの外に出さないでください。

テスト:
- `npm test`(`tests/unit/`):暗号部分(RFC 4493 と NXP の公開テスト値)、受付の判定ルール、本番用の確認係(Firestoreをまねた模型)を確認します。
- `npm run test:integration`:本物のサーバーで、同時タッチや使い回しを確認します。
- `/tools/queue-test.html`:キューとチェックインの契約テスト。dev環境、全部0の鍵で動かします(`npm run test:e2e` でも自動で動きます)。
